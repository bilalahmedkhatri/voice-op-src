# Localization

All page routes share `app/[locale]`; English content and components are reused. Supported URL prefixes are `en`, `ru`, `pt`, `fr`, `es`, `nl`. Portuguese uses `pt-PT` for HTML and formatting. Unprefixed pages redirect to English. APIs, assets, gateway credentials, ownership and generation-language settings are separate from display locale.

## Messages

- `messages/en.json` is compiled from source-owned UI copy, including public layouts and metadata. `messages/blog/en.json` contains the existing articles. Blog publication membership is determined by the original English definitions before translation.
- Other locale JSON files contain translations only. Missing entries fall back to English. Blog catalogs stay on the server; article text is not sent to dashboard clients.
- `useCopy`/`getCopy` are small adapters to next-intl's translators. Stable source IDs deduplicate shared text; escaping preserves English apostrophes, markup-like examples and interpolation. Use complete messages with interpolation/plurals when adding new copy.
- `copyData` applies only to static presentation constants. Never pass user scripts, saved templates, generated results, history, provider data or account records to it. It preserves IDs, values, routes, React elements and the original records.
- Add new translations to the locale catalogs, run `pnpm i18n:compile`, then `pnpm test:i18n` and `pnpm i18n:audit`.

## Current release boundary

All six UI and blog catalogs are populated. Core navigation, hero and voice controls have manually prepared translations; the remaining text has locally generated translation drafts. Automated coverage establishes that messages are present and format correctly. Fluent-speaker review is still a release requirement, especially for legal wording, marketing claims and European Portuguese usage.

`messages/readiness.json` is generated by the offline compile command. Incomplete locales remain accessible for review but have `noindex` and are excluded from the sitemap/language alternates. When the full UI and blog catalogs are filled, compilation automatically includes those locales in public indexing. Private workspace routes remain `noindex` in every language.

## Local translation drafts

`messages/sources.json` is the exact source-owned English text registry for review. No credentials, environment files, account records or user-generated content are included.

The development-only `scripts/translate-local-copy.py` runs the pinned Helsinki-NLP OPUS translation models locally. Its separate `--download` operation downloads only public tokenizer/config/safetensors files. The inference path sets Hugging Face offline mode, loads only local files and never exports the app text. Portuguese uses the generic Portuguese target with European terminology corrections and manual core translations: the model's listed `pt_PT` token produced mixed Spanish during validation. No translation service or Python/model runtime is used by the deployed app.

Brand names, URLs, emails, numbers and interpolation tokens are protected during translation. The generated catalogs are drafts: fluent-speaker review remains necessary, particularly for legal wording, marketing tone and European Portuguese terminology. Core navigation and voice controls have manually prepared translations in `messages/core-translations.json` which compilation reapplies over drafts.

## Verification

- `pnpm test:i18n`: ICU formatting, exact English text preservation, fallback, Russian plurals, source-data immutability, stable blog publication membership/IDs/slugs.
- `pnpm test:ownership`: existing isolated account, gateway, retry, library and guest-mode regressions plus localized OAuth destinations.
- `node tests/localization-routes.cjs`: read-only smoke against a running app, defaulting to `http://localhost:3000`. Override with `I18N_TEST_BASE_URL`. Checks all page routes in every locale, query-preserving legacy redirects and localized 404s. It never synthesizes, publishes or pays.
- `pnpm exec tsc --noEmit --incremental false` and `pnpm build`.

Browser checks should cover the public and workspace selectors, query/hash preservation, sidebar links, auth return destinations, long text and 390px mobile widths. Runtime/provider, production database, payments, hosted deployment and fluent-language quality require separate verification.
